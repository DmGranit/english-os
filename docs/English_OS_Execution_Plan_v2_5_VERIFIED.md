**Причина (выяснено гейтом 0.1).** +528 Б = недокоммиченное тело `db.nudge_band` («руль

**Поправка к гипотезе §0 (честно).** Исходная рамка строилась на «две КК-сессии пишут код,
ГД не независим, возможна запись мимо git». По факту **код вёл только владелец, через git,
с коммитами**; соседняя сессия и контролёр трогали лишь документы. Значит «ГД 72 289 = диск» —
просто облачная синхронизация рабочего диска, а не третий пишущий источник. Угрозы двух
пишущих агентов в этой сессии **не было** — это была ложная тревога поверх реального бага.
_(Гипотеза возникла из реплики владельца «одна сессия распоряжается и диском, и ГД»; снимается
уточнением «кодил один». Если появится вторая пишущая в код — write-lock и «коммит-перед-

**Исправление.** Восстановительный коммит `de4b3d3` (`fix: db-половина руля сложности`):

**Урок, закреплённый двумя инцидентами дня → правило:** «отлажено на диске» и «опубликовано
в git» — РАЗНЫЕ события. Релиз закрыт только когда: код отлажен на диске → тесты зелёные →
**коммит → push → `origin` содержит то же (хеш сошёлся)**. Незакоммиченный (`nudge_band`) или
незапушенный (`f19c345` до пуша) код — это «истина на одной машине», источник дрейфа.
Дисциплина: чистый `git status` + `git push` + сверка, что долетело, после каждого батча.

**Правило контура чтения контролёра:** истину о коде и git-состоянии контролёр читает из
**`origin` (GitHub)**, не из ГД. ГД показывает черновик на диске, `origin` — опубликованный
чистовик; `git push` ГД не двигает. Для приёмки коммитов/пушей — только `origin`.

**Follow-up (намечено, по слову владельца): миграция канона в бот-репо под git.** Планы (этот
файл, Roadmap) и Decision_Log переносятся в `english_os_bot/docs/` под git → весь канон (код +
план + журнал) в одном `origin`, «два контура» (ГД↔git) перестают быть проблемой. ГД остаётся
чистым бэкап-зеркалом диска.
