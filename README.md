# English OS — бэкенд телеграм-бота (скелет)

Деловой английский по методологии English OS: сетевое знание, DNA-идеи,
Thinking Frames, spaced repetition.

## Архитектура

```
content (JSON seed)─┐
                    ▼
              ┌──────────┐   due_today / promote / review   ┌──────────┐
  Telegram ──▶│  bot.py  │◀────────────────────────────────▶│  db.py   │── SQLite
              └────┬─────┘                                   └──────────┘
                   │  ЯДРО + модуль режима                        ▲
                   ▼                                              │ pending→confirm
              ┌──────────┐        ┌──────────┐                    │
              │prompts.py│        │  llm.py  │── OpenAI/Anthropic  │
              └──────────┘        └──────────┘                    │
```

- **Канон — SQLite.** JSON/Excel — одноразовый seed и архив. Пишет только бот.
- **Контент и состояние разделены:** `content` (онтология) vs `state` (прогресс SRS).
- **Промпт модульный:** на каждый вызов `ЯДРО + модуль текущего режима` (≈900 токенов
  вместо ~2700 у монолита).

## Запуск

```bash
pip install -r requirements.txt
python seed.py                          # один раз: контент JSON → SQLite
export TELEGRAM_TOKEN=...                # токен бота от @BotFather
export LLM_API_KEY=...                   # ключ модели
export LLM_PROVIDER=openai               # openai | anthropic
export LLM_MODEL=gpt-4o-mini             # дешёвая модель под бота
python bot.py
```

Без `LLM_API_KEY` бот отвечает заглушкой — каркас можно гонять локально.

## Что реализовано

- SRS Лейтнера (1→3→7→14→30), сброс в box 1 при «забыл».
- Дневной лимит ввода новых слов (`DAILY_NEW_CAP=5`) — защита от лавины повторений.
- Ввод самых ценных слов первыми (приоритет = freq × useful).
- Интейк новых слов: агент → `pending` → подтверждение человеком → `content` (origin=added).
- Бэкап SQLite в конце сессии (`backups/`).
- Повторение в направлении RU→EN (продакшен, не узнавание).
- Карточный режим повторения: по одному слову, кнопки «👁 Показать ответ» и
  «✅ Вспомнил / ❌ Забыл» дёргают `db.review()` — цикл SRS замкнут, работает без LLM.
- Калибровка направления recall по зрелости слова: box 1–2 — узнавание (EN→RU),
  box ≥ `PRODUCTIVE_FROM_BOX` (3) — продукция (RU→EN). Основано на исследованиях
  retrieval-direction (низкому уровню — рецепция, зрелому — продукция).
- Контракт «бэкенд → агент»: `db.format_for_agent()` — единый формат данных слова.
- Разбор итога сессии: модель выдаёт строгий JSON-блок (`reviewed`/`add`), бэкенд применяет —
  `reviewed` → SRS (`db.review`), `add` → очередь `pending` (`db.apply_session_summary`).
  Цикл обучения замкнут с обоих концов.
- Очередь подтверждения: команда `/pending` показывает добавленные ИИ слова с кнопками
  «Добавить / Отклонить» (`db.confirm_pending` / `db.reject_pending`); защита от дубликатов.
- Запрашиваемая сеть: `family`/`collocations`/`phrasal` вынесены в связанные таблицы
  (`word_family`/`word_collocation`/`word_phrasal`, наполняются при seed). Запросы:
  `words_by_root`, `words_by_idea`, `search_collocation`, `neighbors`. Текстовые поля в
  `content` сохранены — старый код не затронут.
- Движок структурных ошибок (L1-агностичный): `errors`-блок из ИТОГ пишется в таблицу
  `errors` (категории word_order/article/preposition/tense_aspect/agreement/word_choice);
  команда `/mistakes` показывает повторяющиеся паттерны (`error_patterns`/`recent_errors`).
- Режим чтения (понятный вход i+1, правило 98%): `/read` строит текст из ~98% уже
  освоенных слов (`mature_words`, box≥3/known) + ~2% целевых новых (`target_words`),
  LLM-режим `INPUT`. Закрывает пробел по вводу (Krashen/Nation): не только продукция,
  но и понятный input нужного уровня сложности.
- Описания слоёв подключены: этимология корней («1. Roots») и пояснения фреймов
  («7. Thinking Frames») грузятся в `root_ref`/`frame_ref` при seed и встраиваются в данные
  для ИИ (`format_for_agent`) — модель получает ПРОВЕРЕННУЮ латынь, а не выдумывает.
  Лукапы: `root_info`, `frame_info`. Справочники приведены в соответствие словам (без дрейфа).
- A/B-инструментовка (честная проверка УТП «сеть vs плоско»): карточки REVIEW
  назначаются `layered`/`flat` (`_variant`); вариант и время ответа пишутся в `reviews`
  (`variant`, `ms`); сводка — команда `/abstats` (`db.variant_stats`). Принцип
  «сеть — архитектура, а не доказанный буст» зафиксирован в `../positioning_honest.md`.
  На n=1 это направленный сигнал, не доказательство — полноценный A/B нужен на когорте.
- Наполнение базы (`enrich.py`): слово → ИИ генерирует полный 7-слойный JSON (с опорой на
  существующие DNA-идеи и фреймы, корень — только при уверенности) → валидация/клампинг →
  очередь `/pending` на подтверждение. Защита от дублей. Требует `LLM_API_KEY`.
- Измеримость без BEC (CEFR can-do): банк деловых «могу сделать X» (`db.CANDO`, уровни
  A2–B2) привязан к реальным сценариям; `/progress` (`cando_progress`) показывает готовность
  по доле освоенных слов сценария. Это прокси по словарю, не сертификация. BEC как
  бенчмарк снят — линейка свёрнута во всём мире, кроме Китая (см. `../positioning_honest.md`).

## Устойчивость (гигиена)

- Соединения с SQLite закрываются после каждой операции: `_conn` — контекст-менеджер
  (commit при успехе / rollback при ошибке / close всегда). Нет утечки дескрипторов.
- Сбой сети или API не роняет бота: `llm.chat()` ловит ошибки и возвращает мягкое
  сообщение пользователю; таймаут запроса к модели — 30 с.
- История диалога ограничена последними `MAX_HISTORY=20` сообщениями — контекст
  (и стоимость токенов) не растёт без предела.
- Единственный источник промпта — `prompt.md`; дублирующий файл удалён.
- ИТОГ не теряется: парсер берёт ПОСЛЕДНИЙ ```json-блок ответа (раньше мог схватить
  пример из текста), а финальный вызов идёт с повышенным лимитом токенов
  (`SUMMARY_MAX_TOKENS=1600` — отчёт + JSON в 600 не влезали, JSON обрезался).
- Тесты: `python -m pytest` — SRS-переходы (`review`), дневной лимит (`promote_new`),
  контракт ИТОГ (`_extract_summary`, `apply_session_summary`). База — временная,
  рабочая `english_os.db` не трогается.
- Повторный `seed` безопасен: контент обновляется upsert-ом (`ON CONFLICT DO UPDATE`),
  внешние ключи не нарушаются, прогресс пользователя (`state`) сохраняется.
